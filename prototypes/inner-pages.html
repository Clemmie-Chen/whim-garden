home-rentor: 一个扣扣J人的找房比房小工具

自如贝壳总是展示装修图，看得人眼花缭乱，但通勤、位置、价格、性价比，多看几套就晕了。借助这个小工具，你可以收集候选房源，在地图上一眼看清、对比。

Jun 152026 Contents
    起点是一个很具体的痛点：在上海租房，看完一圈房子，脑子里全是「这套阳台不行那套厨房太小」，刚看完五套，过两分钟后全忘了。这个项目是为了成为你的租房临时大脑 dumper，把临时记忆容量给腾出来。
    仓库：github.com/Clemmie-Chen/home-rentor

    一句话

    候选房源散落在贝壳、小红书、中介微信里，信息对不齐、通勤靠脑补。于是做了个工具：把所有候选房源录到一张带地铁线的地图上，标面积/月租/小区、自动算通勤、记看房后的状态和备注，最后在地图上直观判断哪套值得租。

    为什么自己做

    现成的租房 App 解决的是「找房源」，但我真正的痛点是看房之后的决策：

    • 同一个小区不同中介报价不一样，得自己并排比；
    • 通勤不是「离地铁多远」，而是「到地铁站、实际工作地要多久」；
    • 在软件上看完房，脑子里全是具体的装修和照片，没法横向比较真正的房子质量。

    几个真正花了时间的技术点

    1. 坐标系是个隐形大坑

    高德 API 返回 GCJ-02，而 OSM 底图 / Leaflet 用 WGS-84。两者差 300–600 米——足够把一套房子标到隔壁小区。

    • 入库时 eviltransform.gcj2wgs()：高德坐标 → 存储/上图
    • 算通勤时再 wgs2gcj() 转回去喂给高德路线 API

    2. POI 搜索会「张冠李戴」

    搜「平吉二村」，高德第一个返回的可能是隔壁的「莲花新城」。所以选 POI 时优先取名字里包含查询词的那个。

    3. 自然语言录入，但解析逻辑有两份

    梧桐花园 90平 8000/月 两室两厅 电梯 朝南

    网页（parseInput）和飞书机器人（bridge.py 的 parse_text）两份解析器必须保持同步。原文是唯一数据源：解析器升级后，老房源会自动补全新字段。

    4. 家用宽带没有公网 IP

    Mac mini 上 server.py 由 launchd 常驻，再用 Cloudflare Tunnel 出站打洞。踩的坑：不能用 brew services start cloudflared。

    如果重来会改什么

    • 服务端目前无鉴权，拿到 URL 就能读写。
    • 「两份解析器」是债。
    • 「最后写入者赢」的同步在多设备同时编辑时会丢数据。

    技术栈速查

    层选型理由
    地图Leaflet + CartoDB Positron轻、免费、底图素净不抢房源标记
    坐标转换eviltransformGCJ-02 ↔ WGS-84 必需
    后端Python http.server零依赖、单文件、够用
    地理/通勤高德 Web 服务 API国内数据准，免费额度 ~5000/日
    部署Mac mini + launchd + Cloudflare Tunnel家用宽带无公网 IP 的出站方案
